01 — What the audit found

Six problems, and only one of them is taste

Every number below is counted from the working tree, not estimated. The headline: there are two design systems in this app, and the wrong one won.

1,109occurrences

Hardcoded white/N utilities bypass the token layer

Across 73 files. globals.css defines a proper semantic ramp — --c-surface, --c-text-2, --c-border — but token utilities are used only 352 times. Raw bg-white/5 outnumbers the system three to one.

Root cause
3 of 4sections broken

Light mode is shipped but non-functional outside /me

ThemeToggle flips html.light to a #f4f4f0 ground, but /org (524 hits), /admin (134) and /team (104) paint text in text-white/40. On paper that is invisible. The feature is a switch that breaks the app.

User-facing bug
16items, one row

Navigation is three stacked horizontal bars

Global nav, then a section sub-nav, then page tabs — ~150px of chrome before any data. The org sub-nav packs 16 links into a single flex gap-6 with no wrap or overflow handling; it collapses below roughly 1400px.

Blocks scale
3stat cards

The same primitive, re-implemented per section

StatCard, StatCardWithDelta and a private Card inside SummaryCards render near-identical tiles with different padding, type sizes and colors. SectionCard, DataTable and PageHeader exist for team-org only, so /me re-rolls each one inline.

Drift
0chart tooltips

Charts are hand-rolled SVG with no shared grammar

Every chart invents its own viewBox, scale, height and label style; series colors are picked ad hoc from Tailwind's default palette. Nothing has a hover state, an axis, or a legend — on a product whose entire job is reading data.

Core surface
4page widths

No layout contract

Root main is full-bleed px-6; /org sets max-w-7xl px-4; /me pages each declare their own max-w-5xl; others use 4xl or 6xl. Content jumps width as you move between sections.

Polish

Worth saying plainly: the existing type stack (Syne / DM Sans / IBM Plex Mono) and the lime signature are good, distinctive choices. This proposal keeps all four. The revamp is structural.

02 — The system

Instrument

A console you read at a glance, not a page you scroll. Depth comes from a hairline and a surface step — no shadows, no gradients. Every number is monospaced and tabular so columns align. The lime stops being decoration and becomes a pointer: it marks where you are, what has focus, and the one number that matters. It is never a status and never a series.

04 — Calls I'd like you to weigh in on

Four decisions worth a conversation

Everything else in this proposal I'd just build. These four change the shape of the work.

01

Rail versus keeping horizontal navigation

The rail is what makes 16 org sections and 10 admin pages survivable, and it scales as you add more. The cost is a real change to app/layout.tsx and every section layout, and it spends ~214px of horizontal room on wide tables. The alternative is a command palette plus a shorter grouped sub-nav — cheaper, but it hides structure behind a keystroke.

02

Is light mode actually a supported product?

Right now it is half-built, which is worse than either alternative. Fixing it properly is a meaningful share of the token migration. Deleting ThemeToggle and committing to dark-only is a legitimate, cheaper answer for a developer tool — but it should be a decision, not the status quo. This proposal assumes we keep it.

03

Charts stay hand-rolled, or take a dependency

I'd keep them hand-rolled: server-rendered SVG with a shared scale/axis/legend module and a thin client wrapper for hover. That fits the Server Components default and adds zero kilobytes. A charting library would be faster to reach parity but pulls ~50KB into the client and forces most chart pages to 'use client'.

04

Big-bang migration, or section by section

1,109 replacements is largely mechanical and mostly scriptable. Doing it in one pass means one review with no mixed-system window; doing it per section keeps PRs reviewable but leaves the app visibly inconsistent for weeks. I'd lean toward one codemod PR for the token swap, then per-section PRs for layout.

Four phases, each shippable alone

Ordered so the highest-leverage fix lands first and nothing depends on a later phase.

  • two-token accent
  • contrast fixes on ink-2
  • light mode works everywhere

Phase 4

Chart grammar

Shared scales, axes, legends, and a hover layer — applied across every existing chart.

  • fixed series assignment
  • crosshair + tooltip
  • empty / low-data states
